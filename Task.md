# Task.md — «Пульс» / цифровой деканат будущего

> **Статус:** техническое задание и план реализации конкурсного **прототипа**, не действующего сервиса вуза.  
> **Обновлено:** 18.11.2026. **Доступность демо:** как минимум по 28.11.2026 включительно.  
> **Главный принцип:** законченные пользовательские сценарии, настоящая серверная авторизация и изоляция данных важнее количества экранов.

## 1. Цель и продуктовая гипотеза

Студент не должен искать расписание в одном месте, оценки — в другом, а состояние запроса в деканат — в третьем. «Пульс» объединяет эти действия и показывает **что важно прямо сейчас**: следующее занятие, перенос, ближайший дедлайн, ситуацию с зачётами и состояние заявок.

**Целевая аудитория:** студент бакалавриата/специалитета, чаще открывающий кабинет с телефона; вторичная аудитория — сотрудник деканата, если на него останется время. Все персонажи, вузы, преподаватели, группы и записи в демо вымышлены.

**Главные продуктовые принципы:**
1. От главной страницы до расписания, оценок или новой заявки — максимум 1–2 нажатия.
2. На каждом экране есть ответ на вопрос «что мне делать дальше?».
3. При изменении расписания явно показаны **что изменилось** и **когда**; нельзя тихо переписывать старое занятие.
4. Заявка не исчезает после отправки: видны номер, дата, текущий статус и история.
5. Все данные идут с сервера после проверки сессии, а не из подменяемого `user_id` в браузере.
6. Даже на 360 px нет горизонтального скролла, обрезанных кнопок и неработающих сценариев.

**Уникальная концепция:** главный экран «Мой день» + блок «В фокусе», объединяющий события из расписания, оценок, сессии, заявок и объявлений. В MVP это **детерминированные правила**, не «магический ИИ», который выдумывает информацию. ИИ обязателен как **помощник в разработке**; подключать внешнюю LLM во время работы кабинета необязательно.

## 2. Технологии и ограничения

| Слой | Решение | Зачем |
|---|---|---|
| Frontend | **React + TypeScript + Vite** | Быстрый адаптивный SPA с типизированными контрактами |
| UI | Tailwind CSS, доступные headless-компоненты, lucide-react | Единая дизайн-система, удобная мобильная навигация; лицензии проверить |
| Клиентские данные | TanStack Query + React Router; формы React Hook Form + Zod (по необходимости) | Обновление после мутаций, загрузки и ошибки, маршруты |
| API | **Python + FastAPI + Pydantic v2** | OpenAPI и валидация запросов |
| Линт/формат Python | **Ruff** (`ruff check`, `ruff format --check`) | Единый стиль, проверка импортов, CI quality gate |
| БД | **PostgreSQL** | Транзакции, ограничения, разделение персональных данных |
| Доступ к БД | SQLAlchemy 2.x + Alembic + драйвер asyncpg | ORM, явные миграции, асинхронный API |
| Пароли/сессии | Argon2id (`pwdlib[argon2]` или эквивалент); opaque session в HttpOnly cookie, сессии в Postgres | Пароли не в открытом виде, отзыв сессий и отсутствие access token в `localStorage` |
| Инфраструктура | **Docker Compose v2**, multi-stage Dockerfiles, Caddy как reverse proxy/TLS | Развёртывание одной командой, frontend/API на одном origin |
| Тесты | **pytest, pytest-asyncio, httpx, testcontainers[postgres]**, frontend unit tests и Playwright | Проверка настоящего Postgres и основных сценариев в браузере |
| CI/CD | GitHub Actions **или** CI на выбранном Git-хостинге | Линт, тесты, сборка, smoke; деплой с защищёнными секретами |
| Очереди (P1) | Redis + Celery worker/beat | Только если нужны асинхронные уведомления, задачи и периодические дедлайны |

**Не усложнять MVP:** микросервисы, Kubernetes, event bus, внешняя LLM, файловое хранилище, многофакторный вход и полная ERP-интеграция не нужны для оценки работающего прототипа. Архитектура — **модульный монолит** FastAPI с чёткими границами доменов.

**Хостинг:** VPS/площадка с проверенной доступностью из России без VPN; домен, HTTPS, работающий сертификат и публичный URL. Не рассчитывать, что доступность из другой страны доказывает доступность из РФ. Реального вуза и его системы не подключать.

### 2.1 Линтер и форматирование Python: Ruff (обязательно)

Ruff — **единственный обязательный линтер и форматтер Python** в MVP (не добавлять одновременно Black/isort/flake8 с конфликтующими настройками). Настройка в `backend/pyproject.toml`:

```toml
[tool.ruff]
target-version = "py312"
line-length = 100
extend-exclude = [".venv", "__pycache__", "alembic/versions"]

[tool.ruff.lint]
select = ["E4", "E7", "E9", "F", "I", "UP", "B", "SIM"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
line-ending = "lf"
```

Воспроизводимые команды из директории `backend/` после установки dev-зависимостей:

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
# Исправление перед PR (посмотреть diff, не слепо переписывать код):
uv run ruff check . --fix
uv run ruff format .
```

В CI **обязательны** `ruff check .` и `ruff format --check .`; для будущего проекта можно добавить `mypy`/`pyright`, но это **отдельная** проверка типов, не замена Ruff. Запрет на blanket `# noqa` и исключение целых рабочих модулей из линтера; исключения объяснять в комментарии/PR. Файл `pyproject.toml` должен закреплять Ruff в dev-зависимостях выбранного менеджера и lock-файле.

|---|---|---|

Seed должен быть повторяемым и идемпотентным, без затрагивания чужих данных.

## 4. Обязательные сценарии (MVP / P0)

### S1. Вход, выход, профиль

- `/login`: логин и пароль, валидация, видимая ошибка неверных данных, состояние загрузки.
- При успешном входе сервер создаёт сессию; `/api/v1/auth/me` возвращает текущего пользователя; авторизация сохраняется при обновлении вкладки.
- `/profile`: ФИО, факультет, направление, курс, группа. Редактирование учебных атрибутов студенту запрещено.
- «Выйти» удаляет серверную сессию и cookie; защищённые страницы после выхода недоступны.
- Гость, открывший `/app/*`, перенаправляется на `/login`, не видя приватных данных даже на долю секунды.

**Готово, если:** два аккаунта входят, видят различающиеся профили; после logout любой защищённый endpoint возвращает `401`.

### S2. Расписание

- `/app/schedule`: вкладки **Сегодня / Неделя**, понятная дата, список занятий с временем, дисциплиной, типом, аудиторией и вымышленным преподавателем.
- У занятия доступны состояния `scheduled`, `moved`, `cancelled`; изменения показывают старые и новые параметры и время обновления.
- Есть содержательные пустые состояния «Сегодня нет занятий» и «На этой неделе занятий нет».
- Неделя считается по `Europe/Moscow` для демо; API отдаёт ISO 8601 с корректным timezone и не создаёт перенос на неверный день.

**Готово, если:** студент видит свою группу, перенос отличим от обычной пары, другая группа не раскрывается подменой параметров.

### S3. Успеваемость и сессия

- `/app/study`: дисциплины, текущие оценки, статус зачёта/экзамена и прозрачная сводка «Сдано X из Y».
- Раздел «Сессия»: ближайшие экзамены/зачёты, даты и статусы; **не** выдавать прогнозы или «средний балл» за официальные сведения вуза.
- Для отсутствующих оценок показывать «Пока нет оценок», а не ноль.
- Правило расчёта агрегатов описать в коде, протестировать на граничных случаях.

**Готово, если:** оценки и сессия отличаются между аккаунтами, фильтрация по текущему студенту выполняется на сервере.

### S4. Заявки и справки

- `/app/requests`: список **только своих** заявок с типом, датой, статусом; подробности с хронологией событий.
- `/app/requests/new`: выбор типа (например, «Справка об обучении», «Заявление в деканат»), валидируемое поле комментария, при необходимости цель и способ получения. Не собирать лишние личные данные.
- `POST /api/v1/requests` действительно создаёт запись в PostgreSQL, возвращает `201`, публичный `UUID` и первоначальный статус `new`.
- Состояния: `new → in_progress → ready` либо `rejected`; **студент не меняет статус сам**. История содержит время и краткую причину. Для демонстрации разных статусов использовать подготовленные seed-заявки; в MVP отправленная заявка может оставаться `new`.
- После создания карточка сразу видна в списке, переживает перезагрузку браузера и повторный вход. Двойное нажатие предотвращено disabled-кнопкой; дополнительно поддержать `Idempotency-Key` для защиты от повторной отправки при ретраях (желательно P1).

**Готово, если:** студент создаёт заявку за несколько действий и не может прочитать чужую по UUID, даже зная URL; сервер возвращает `404` на чужой UUID.

### S5. Уведомления

- `/app/notifications`: индивидуальные объявления, изменения расписания, приближение сессии/дедлайнов и изменение заявок.
- «Прочитать» — серверная мутация, сохраняющая `read_at`; счётчик непрочитанных обновляется без перезагрузки.
- Каждое уведомление ведёт на **существующий доступный** объект или отображает понятный текст без ссылки.
- Никаких уведомлений о чужих заявках или оценках. Источник уведомления и время указаны.

**Готово, если:** прочтение сохраняется после нового входа; попытка отметить чужое уведомление не изменяет запись.

### S6. Главная страница «Мой день»

- `/app`: приветствие, следующее занятие или «Сегодня свободно», ближайшее событие сессии, активные заявки, 1–3 важные записи «В фокусе», быстрые действия.
- Блок «В фокусе» приоритизирует **известные факты**, например отмену пары сегодня, экзамен в ближайшие 3 дня, заявку `ready`. У каждого пункта — конкретная ссылка на исходную запись.
- Один клиентский запрос `/api/v1/dashboard` может агрегировать эти данные сервером, но не обходит авторизацию.

**Готово, если:** на 360 px важная информация и основные действия доступны без сложных меню, при пустых данных видны понятные альтернативы.

- Не загружать внешние картинки/шрифты ради красоты без проверки лицензии и необходимости; системный шрифт допустим.

## 7. API-контракт: точные запросы, JSON-ответы и ошибки (P0)

**Это обязательная спецификация для backend и frontend, а не перечень предполагаемых роутов.** Агент реализует именно описанные формы данных; изменение полей сначала вносит в этот раздел, затем в Pydantic-схемы, OpenAPI, frontend-типы и тесты. Примеры UUID, даты, ФИО, дисциплины и имена далее **вымышленные**; строки вида `<...>` — заглушки для объяснения, не секреты и не фактические demo credentials.

### 7.1 Общие правила HTTP/JSON

- Префикс **`/api/v1`**, JSON в UTF-8, `Content-Type: application/json` для запросов с телом. Сервер возвращает `application/json`; исключение — `204 No Content`, у которого нет тела.
- Frontend и API находятся на одном origin; браузер выполняет `fetch(..., { credentials: "include" })`. Пароль передаётся **только** на `/auth/login` по HTTPS. Токен серверной сессии передаётся **только HttpOnly-cookie**, **не** в JSON и **не** в `localStorage`.
- Все приватные маршруты требуют cookie и действующую сессию. Исключения: `POST /auth/login`, `GET /health/live`, `GET /health/ready`.
- Для `POST/PATCH/DELETE`, **кроме login**, обязателен заголовок `X-CSRF-Token`, полученный через `GET /auth/csrf`; обязательна проверка `Origin`. Вход дополнительно защищён проверкой `Origin` и типа тела; `SameSite` не заменяет CSRF.
- **Нельзя** передавать `student_id`, `user_id`, `owner_id`, `group_id` в запросах студента для выбора чужих данных. Сервер выводит студентский scope из сессии. Лишние поля в Pydantic body → `422 VALIDATION_ERROR` (`extra="forbid"`). Внутренние пароли, session-token, hash и `csrf_token` не попадают в профиль/обычные ответы.
- Даты-времена — ISO 8601 с явной зоной (напр., `2026-11-19T09:00:00+03:00`, либо `Z`); дата без времени — `YYYY-MM-DD`; UUID — строка. В Postgres время хранится в UTC (`timestamptz`), учебные дни/недели рассчитываются для демо в `Europe/Moscow`.
- В коллекциях используем `items` + `pagination` (`page` от 1, `page_size` от 1 до 100, default 20; сортировка детерминированная). Поля с отсутствующими значениями **`null`**, если они включены в объявленную схему; не заменять `null` пустой строкой, нулевой оценкой или фиктивной датой.
- Ответы **не** оборачивать произвольно в `data`, `result`, `payload` и пр. Формат каждого успешного JSON строго указан ниже. Успешный `204` не содержит JSON. Для ошибок используется единая схема из §7.16.
- Все модели запросов и ответов — `Pydantic v2`, явно указаны в `response_model`; `openapi.json` — генерируемая проекция **этого** контракта. По умолчанию внешние API-поля — `snake_case`.

### 7.2 Авторизация: `POST /api/v1/auth/login`

**Доступ:** гость. **Заголовок:** `Origin: https://<your-domain>`. **Request body:**

```json
{
  "username": "demo.alina",
  "password": "<пароль_для_демо_из_окружения>"
}
```

Правила: `username` — непустая строка 3–64 символа, `password` — строка 1–256 символов, лишние ключи запрещены. Валидация формата не должна давать возможность выяснить существование логина. При успешном входе сервер сверяет **Argon2id**, создаёт opaque-сессию, сохраняет её hash и отправляет `Set-Cookie: __Host-session=...; HttpOnly; Secure; SameSite=Lax; Path=/` в production.

**`200 OK` response JSON:**

```json
{
  "user": {
    "id": "b1c8061c-0d57-416a-9a25-2146aaaab111",
    "username": "demo.alina",
    "role": "student"
  },
  "session": {
    "expires_at": "2026-11-25T09:00:00Z"
  }
}
```

В `session` **нет** токена, а в `user` — password hash. Ошибки: `401 INVALID_CREDENTIALS` (неверный логин **или** пароль, один и тот же ответ), `422 VALIDATION_ERROR`, `429 RATE_LIMITED`, `403 ORIGIN_FORBIDDEN`.

### 7.4 CSRF: `GET /api/v1/auth/csrf` и выход: `POST /api/v1/auth/logout`

`GET /auth/csrf`: авторизованный GET без тела; `200 OK`:

```json
{ "csrf_token": "<пример_не_реального_csrf_токена>" }
```

Токен привязан к текущей серверной сессии, ответ `Cache-Control: no-store`; это **не** access token и не передаётся сторонним доменам. Для logout и остальных мутаций browser посылает `X-CSRF-Token: <значение из /auth/csrf>`.

`POST /auth/logout`: пустое тело (не JSON `{}`), cookie + валидные `X-CSRF-Token`/`Origin`. Успех: **`204 No Content`**, **тела ответа нет**, сервер отзывает сессию и удаляет cookie через `Set-Cookie`. Последующие приватные запросы с ранее выданным cookie → `401`. Ошибки `401 UNAUTHORIZED`, `403 CSRF_INVALID` / `ORIGIN_FORBIDDEN`.

### 7.6 Расписание: `GET /api/v1/schedule`

**Query:** `view=today|week` (default `today`), `date=YYYY-MM-DD` (по умолчанию текущая дата в `Europe/Moscow`). **Пример:**


`date` — дата внутри запрашиваемого диапазона: для `week` сервер определяет понедельник–воскресенье; для `today` — ровно выбранный день. ### 7.10 Мои заявки: `GET /api/v1/requests`

**Query:** `status=new|in_progress|ready|rejected` (необязательный), `page=1` (default), `page_size=20` (default, max 100). **Пример:**

```http
GET /api/v1/requests?status=new&page=1&page_size=20
```

**`200 OK` response JSON:**

```json
{
  "items": [
    {
      "id": "f4aeac07-3e6a-4f7f-a234-67a9f7f1e41a",
      "type_code": "STUDY_CERTIFICATE",
```

Сортировка: `created_at DESC, id DESC`; `total` учитывает **только собственные** заявки и применённый фильтр. В пустом списке `items=[]`, `total=0`. `student_id` в query **не принимается**. Ошибки `401`, `422` при некорректном статусе/пагинации.

### 7.11 Создание заявки: `POST /api/v1/requests`

**Headers:** session-cookie, `Origin`, `Content-Type: application/json`, `X-CSRF-Token`. **Request JSON (справка):**

```json
{
  "type_code": "STUDY_CERTIFICATE",
  "fields": { "purpose": "work", "delivery_method": "digital" },
  "comment": "Нужна для оформления на практику"
}
```

**Альтернативный request JSON (заявление):**

```json
{
  "type_code": "DEAN_OFFICE_STATEMENT",
  "fields": { "topic": "study" },
  "comment": "Прошу уточнить порядок оформления индивидуального учебного плана."
}
```

Поля `type_code` (строка из `/request-types`) и `fields` (объект) обязательны; `comment` — необязательный `string|null` для справки (0–500), обязательный для заявления (1–1000 непустых после `strip`). Все вложенные поля проверяются по соответствующему `fields_schema`. **Не принимаются** `student_id`, `status`, `id`, `created_at`, `history`: наличие → `422`. Новый владелец всегда `current_student.user_id`; начальный статус **`new`**, история создаётся **в той же транзакции**.

**`201 Created` response JSON** (`Location: /api/v1/requests/f4aeac07-3e6a-4f7f-a234-67a9f7f1e41a`):

```json
{
  "id": "f4aeac07-3e6a-4f7f-a234-67a9f7f1e41a",
  "type_code": "STUDY_CERTIFICATE",
  "type_title": "Справка об обучении",
  "status": "new",
  "fields": { "purpose": "work", "delivery_method": "digital" },
  "comment": "Нужна для оформления на практику",
  "created_at": "2026-11-18T10:00:00+03:00",
  "updated_at": "2026-11-18T10:00:00+03:00",
  "history": [
    {
      "id": "c943dfe3-070e-414b-a641-454046ce0672",
      "from_status": null,
      "to_status": "new",
      "note": "Заявка создана",
      "created_at": "2026-11-18T10:00:00+03:00"
    }
  ]
}
```

Ошибки: `401 UNAUTHORIZED`, `403 CSRF_INVALID|ORIGIN_FORBIDDEN`, `422 VALIDATION_ERROR` (невалидные поля/тип), `429 RATE_LIMITED` (если настроен предел создания заявок). Повторная отправка без отдельного `Idempotency-Key` создаст новую заявку; клиент блокирует кнопку на время отправки. `Idempotency-Key` с сохранением ключа/ответа в БД и уникальным индексом — **P1, не заявлять реализованным в P0**.

### 7.12 Одна заявка: `GET /api/v1/requests/{request_id}`

`request_id` — **UUID из path**, тело и query отсутствуют. **Пример:**

```http
GET /api/v1/requests/f4aeac07-3e6a-4f7f-a234-67a9f7f1e41a
```

**`200 OK` response JSON** — **точно такая же полная форма**, как `201` создания (§7.11); `history` отсортирована по `created_at ASC, id ASC`. При последующих изменениях `status`, `updated_at`, события истории обновляются, но схема не меняется.

**Ошибки:** `401 UNAUTHORIZED`; `422 VALIDATION_ERROR`, если ID не UUID; **`404 NOT_FOUND` и для отсутствующей, и для чужой заявки**, с одинаковыми полями, кодом и сообщением (идентификатор запроса индивидуален). DAO выполняет `WHERE applications.id = :request_id AND applications.student_id = :current_student_id` в **одном SQL-запросе**, а события истории выбираются **только после** успешной проверки ownership. Нет `PATCH/DELETE` заявки для роли `student`.

### 7.15 Health: `GET /api/v1/health/live` и `GET /api/v1/health/ready`

Оба маршрута публичные, без тела, cookie и параметров, **без персональных данных**.

```json

```

`GET /health/ready` → **`200 OK`**, если БД доступна и соединение устанавливается:

### 7.16 Единая схема ошибок (все роуты)

**Стандартный ответ для ошибки:**

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте введённые данные",
    "request_id": "req-01hxdemo",
    "details": [
      { "field": "fields.delivery_method", "message": "Недопустимое значение" }
    ]
  }
}
```

`details` присутствует **только** при `422`, иначе ключ отсутствует. Внутренние SQL/traceback, фамилии других студентов, существование чужого UUID в `details` и `message` не раскрывать. HTTP-статусы и коды:

| HTTP | `error.code` | Когда |
|---|---|---|
| `400` | `BAD_REQUEST` | Синтаксически некорректный запрос вне Pydantic, если применимо |
| `401` | `UNAUTHORIZED` | Cookie отсутствует, просрочена или отозвана |
| `401` | `INVALID_CREDENTIALS` | Неверные данные при login, без проверки существования пользователя |
| `403` | `FORBIDDEN` | Недостаточно прав роли на действие |
| `403` | `CSRF_INVALID` / `ORIGIN_FORBIDDEN` | Нет/неверный CSRF либо недоверенный Origin |
| `404` | `NOT_FOUND` | Объект отсутствует **либо чужой**, одинаковая форма ответа |
| `405` | `METHOD_NOT_ALLOWED` | HTTP-метод недоступен для маршрута |
| `413` | `PAYLOAD_TOO_LARGE` | Тело запроса превышает 16 КиБ |
| `409` | `CONFLICT` | Конфликт состояния при будущем P1 workflow сотрудника |
| `422` | `VALIDATION_ERROR` | Формат JSON/UUID, enum, диапазон, лишние поля, business-validator |
| `429` | `RATE_LIMITED` | Слишком много попыток входа или создания заявок при включённом лимите |
| `500` | `INTERNAL_ERROR` | Безопасное общее сообщение; логировать `request_id`, не traceback в JSON |
| `503` | `SERVICE_UNAVAILABLE` | БД/необходимый сервис недоступен |

**`404` для чужой и отсутствующей заявки использует одинаковый код и текст.** `request_id` различается между отдельными запросами.

```json
{ "error": { "code": "NOT_FOUND", "message": "Запись не найдена", "request_id": "req-01hxdemo" } }
```

### 7.17 Необязательный P1: API сотрудника (НЕ часть обязательного MVP)

Добавлять только вместе с отдельной ролью `staff`, scope подразделения, аудитом и тестовым staff-аккаунтом; до этого маршруты **не публиковать**.

- `GET /api/v1/staff/requests?status=new&page=1&page_size=20` → `200` с тем же объектом `items/pagination`, что §7.10, но с `student: {"full_name": "Алина Тестова", "group_name": "ИВТ-21"}` в каждой записи и **только** в рамках разрешённого подразделения.
- `PATCH /api/v1/staff/requests/{request_id}/status`, cookie + CSRF + Origin. **Request JSON:**

```json
{ "status": "in_progress", "note": "Запрос принят в обработку" }
```

  **`200 OK` response JSON** (без раскрытия служебной информации):

```json
{
  "id": "f4aeac07-3e6a-4f7f-a234-67a9f7f1e41a",
  "status": "in_progress",
  "updated_at": "2026-11-18T13:00:00+03:00",
  "history_event": {
    "from_status": "new",
    "to_status": "in_progress",
    "note": "Запрос принят в обработку",
    "created_at": "2026-11-18T13:00:00+03:00"
  }
}
```

  Допустимые переходы: `new→in_progress`, `in_progress→ready|rejected`; `new→ready` запрещён. Если статус уже изменился — `409 CONFLICT`, если чужое подразделение или UUID не найден — `404 NOT_FOUND`, если студент пытается обратиться к staff-маршруту — `403 FORBIDDEN`. `status` и событие должны сохраняться в **одной** транзакции.

**Обязательно по каждому endpoint'у:** позитивный тест точной JSON-формы, тест невалидного входа, `401` для гостя и `404`/`403` для чужого ресурса или роли. Недокументированный публичный endpoint не добавлять.

## 9. Безопасность — обязательные инварианты

1. **Server-side authorization:** frontend скрывает чужие ссылки для UX, но не является барьером доступа. Каждая операция с объектом дополнительно проверяет его владельца/область допуска.
2. **Разделение аккаунтов:** `demo.alina` не может прочитать/создать/изменить данные от лица `demo.mark` даже путём подмены UUID, query params, тела запроса или URL.
3. **Пароли:** Argon2id, соль генерирует библиотека; никаких plaintext-паролей, «base64-хешей» или заранее прошитых сессий в БД.
4. **Сессии:** случайный криптостойкий opaque token, в БД хранится только его SHA-256 digest; срок жизни и logout/revocation работают. При login ротация токена, при logout очистка.
5. **Секреты:** не коммитить `.env`, закрытые ключи, demo-пароли, секретные токены. `.env.example` содержит только имена и фиктивные placeholders. Не отдавать ключи/секреты в JS bundle или OpenAPI-примеры.
6. **Защита веба:** TLS в production, ограничение попыток login **общим для всех воркеров** механизмом (Redis/БД или reverse proxy), Origin/CSRF, строгая проверка входных данных, ограничение длины комментариев и размера тела.
7. **Информация об ошибках:** `401` для неавторизованного, `404` для чужого/несуществующего приватного ресурса; не различать причины в публичном ответе.
8. **Приватность:** не логировать cookie, пароль, полный текст заявления; не использовать внешнюю аналитику с персональными данными.
9. **Исходники/зависимости:** лицензии проверены, зависимости версионированы lock-файлами, уязвимости проверены CI.
10. **Доказуемость:** тесты на IDOR, CSRF, logout, cookie-флаги, подмену `student_id`, недоступность защищённых API без сессии.

### 10.1 Ответственность каждого слоя — строго

```text
FastAPI router (api/v1/*.py)
   ↓ Pydantic validation + Depends(current_student, AsyncSession)
Service (services/*_service.py)
   ↓ бизнес-правила, ownership scope, commit/rollback транзакции
DAO (db/dao/*_dao.py)
   ↓ SQLAlchemy 2 select/insert/update с обязательными owner filters
ORM model (db/models/*.py)
   ↓ asyncpg / AsyncSession из db/database.py
PostgreSQL
```

| Слой | Разрешено | Запрещено |
|---|---|---|
| `api/v1/*.py` | Декларация HTTP-метода/пути, `Depends`, `response_model`, перевод результата в DTO | SQL, `session.commit()`, самописная авторизация в каждом handler |
| `schemas/*.py` | Pydantic v2 модели, типы, enum, ограничения, `extra="forbid"` | Работа с БД, побочные эффекты, выдача ORM целиком |
| `services/*.py` | Правила доступа, смена статуса, orchestration DAO, **одна граница транзакции** | Прямые raw SQL, формирование HTTP JSON вручную |
| `db/dao/*.py` | `select`, `insert`, `update`, `delete`, `flush`, эффективные выборки по scope | `commit()`/`rollback()`, `HTTPException`, отправка писем, вызов внешнего API |
| `db/models/*.py` | SQLAlchemy Declarative модели, FK, CHECK, UNIQUE, индексы | Pydantic response DTO, бизнес-операции |
| `db/database.py` | `create_async_engine`, `async_sessionmaker`, request-scoped `AsyncSession`, закрытие соединения | Глобальная разделяемая `AsyncSession`, бизнес-репозитории |
| `infrastructure/redis/` | Только Redis-клиент/адаптеры для optional async/rate-limit | Источник истины для профилей, оценок и заявок |

**BaseDAO (`basedao.py`):** типизированная базовая обёртка над `AsyncSession`, общие методы `get_by_id`/`list` **только для публичных справочников** либо с явно обязательным scope. **Нельзя** делать доступный всем `get_by_id(id)` для приватных ресурсов; в `application_dao.py` использовать `get_for_student(session, application_id, student_id)` и в `notification_dao.py` — `get_for_student` / `mark_read_for_student`. Отдельные доменные DAO содержат запросы с join через enrollment/group и оптимизированные eager loading для предотвращения N+1.

**Сессии и транзакции:** `db/database.py` выдаёт один `AsyncSession` через dependency; он передаётся в сервис, затем в DAO. DAO делает `add`/`flush`, сервис выполняет **один** `commit()` после всех связанных записей (`applications` + `application_events`), при ошибке — `rollback()`. Все читатели работают в контексте сессии; ответы конвертируются в Pydantic DTO до её закрытия. У SQLAlchemy ORM relationship нельзя полагаться на неявный async lazy-load.

**Миграции:** схема создаётся **только Alembic** (autogenerate вручную проверяется), файлы models импортируются в `db/models/__init__.py`, затем `Base.metadata` используется в `alembic/env.py`. `Base.metadata.create_all()` **не** запускается при старте production. Наличие `__pycache__` в примере — следствие исполнения, **не** часть репозитория; все `__pycache__/`, `*.pyc` в `.gitignore` и `.dockerignore`.

## 11. Docker Compose и эксплуатация

**Минимальные сервисы:** `db` (Postgres + persistent volume + healthcheck), `migrate` (одноразовая команда `alembic upgrade head`), `api` (не публиковать порт напрямую в production), `web` (собранный frontend + Caddy, прокси `/api/*` на `api:8000`). В dev допускается Vite server с proxy на API, hot reload и отдельные профили Compose.

**Дополнительно по профилю `async`:** `redis`, `worker` (Celery), `beat` (Celery beat) и при необходимости `mailpit` только для dev. Не включать Redis и Celery «для галочки».

**Требования:**
- `docker compose up --build -d` запускает воспроизводимую dev-версию после заполнения env; документация отдельно описывает production-конфигурацию.
- Healthchecks и `depends_on` в правильном порядке; **миграции запускаются одним процессом**, а не конкурентно в каждом uvicorn worker.
- База на named volume, с резервным копированием/проверкой восстановления хотя бы вручную перед публикацией.
- Нет `5432:5432` на публичном IP production, нет debug mode, секретов в image layers, world-readable `.env`.
- Серверные ошибки и рестарты не сбрасывают заявки и read-status уведомлений.
- Реальный домен + HTTPS; обязательная ручная проверка доступа из РФ и с телефона по мобильной сети.

## 14. Проверки качества и критерии приёмки

### Автоматические проверки (обязательные)

- `pytest`: бизнес-правила, пересчёт статусов, валидация форм и границы дат.
- CI проверяет не менее 80% покрытия строк отдельно для Python (`pytest-cov`) и React/TypeScript (`Vitest` с V8). Для frontend такой же порог действует для инструкций, функций и ветвей. HTML-отчёты сохраняются как артефакты.
- `pytest + testcontainers[postgres]`: поднять изолированную временную PostgreSQL, прогнать **настоящие Alembic migrations**, seed и HTTP API через `httpx`.
- Security tests: `anonymous -> 401`; `student A` видит только A; `student A -> request B UUID => 404`; попытка `student_id=B` в POST не меняет владельца; чужое уведомление нельзя прочитать; повторное использование отозванной сессии запрещено; state-changing без CSRF -> `403`.
- UI: login A → профиль A → расписание A → оценки A → создать заявку A → увидеть её после refresh → logout → login B → нет заявки A; 360 px viewport без горизонтального переполнения.
- CI блокирует merge, если не прошли **Ruff lint и Ruff format-check**, typecheck, tests, frontend build или Docker build.
- Для **каждого** JSON endpoint требуется contract test на структуру тела/ответа из §7, статус, ошибки валидации, а для приватного ресурса — test ownership; OpenAPI сверяется с Pydantic-схемами.
