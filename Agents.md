# Agents.md — рабочие инструкции ИИ-агентам проекта «Пульс»

> **Назначение:** единый договор для Cursor, Claude Code, Codex, GitHub Copilot, Kimi Code, OpenCode, Windsurf и других coding agents.  
> **Проект:** «Пульс» — неофициальный конкурсный прототип цифрового деканата. Все учебные и персональные данные **вымышленные**.  
> **Источник продуктовых требований и полный JSON API-контракт:** [`Task.md`](./Task.md), особенно §7 (HTTP/JSON) и §10 (`db/dao`).  
> **Ожидаемый стек:** Python/FastAPI, PostgreSQL/SQLAlchemy/Alembic, React/TypeScript, Docker Compose, pytest + Testcontainers. Redis/Celery и CI/CD разрешены, но не должны блокировать MVP.

- **Схема БД обязательна к прочтению:** перед созданием или изменением таблиц, связей, FK, индексов и DAO изучи [`docs/database-erd.md`](./docs/database-erd.md) (Mermaid-исходник — `docs/database-erd.mmd`); при любом изменении схемы синхронно обнови ER-диаграмму, SQLAlchemy-модели, Alembic-миграции, DAO и интеграционные тесты.

## 0. Как агент должен начать работу

Перед любыми правками:

1. Прочитай `Task.md` **полностью**, затем `README.md` (если есть) и актуальные файлы затронутых модулей.
2. Сформулируй **узкую задачу** и критерии приёмки. Если задача слишком большая, раздели на вертикальные срезы, но не превращай рабочий сценарий в отдельные несвязанные заглушки.
3. Проверь существующую структуру проекта, миграции, контракты API и тесты. **Не изобретай второй параллельный стек**.
4. Если проект ещё пуст — сначала создай минимальный запускаемый каркас: API health, Postgres, миграции, Vite, Compose, затем переходи к безопасному входу.
5. Определи угрозы и тесты **до** написания нового endpoint'а с персональными данными.
6. После реализации запусти относящиеся к задаче тесты, приведи реальные результаты и список затронутых файлов.
7. Зафиксируй в `docs/ai-process.md` этап, использованный инструмент, исходный промпт, краткую суть ответа, принятые и отклонённые решения, выполненные человеком действия и ссылки на скриншоты. **Не выдумывай историю разработки.**

**Приоритет правил:** безопасность и условия конкурса → `Task.md` → `Agents.md` → существующие ADR/контракты → локальные предпочтения агента. При конфликте пометь его и предложи минимальное исправление, но не ослабляй безопасность.

## 1. Non-negotiable: то, что нельзя нарушать

- Нельзя использовать реальных студентов, преподавателей, оценки, зачётки, логотипы вуза, живые базы, реальные учётные записи или интеграции с университетскими системами.
- На сайте всегда виден смысл предупреждения: **«Конкурсный прототип. Неофициальный сервис. Все данные вымышлены.»**
- Нельзя хранить plaintext-пароли, API keys, реальные `.env`, session tokens, приватные ключи в Git, seed, логах, документации или браузерном bundle.
- **Изоляция student A/student B проверяется на сервере** для каждого приватного endpoint'а. Простое скрытие кнопки или `if (id === currentUser.id)` на frontend не является защитой.
- Нельзя принимать `student_id`, `owner_id`, `user_id` от клиента как источник права доступа. Используй `current_user` из проверенной server-side сессии.
- Нельзя подменять реальные операции муляжами: заявка сохраняется в Postgres, прочтение уведомления сохраняется, logout отзывает сессию, два аккаунта имеют разные данные.
- Нельзя заявлять «тесты прошли», «развернуто», «доступно из РФ» или «ИИ написал код», если это реально не проверено и не зафиксировано.
- Не запускать в production опасные миграции, seed с перезаписью данных, `down -v`, `DROP DATABASE`, удаление таблиц или изменение реальных секретов без явного поручения человека.
- Никаких production credentials или внешних AI API keys в prompts, скриншотах и логах.
- Если правка затрагивает авторизацию, сессии, ACL или схему БД, сначала продумай негативные проверки и сценарий отката.
- Агенты пишут и модифицируют код; человек принимает решения и проверяет результат. В итоговом отчёте обязательно различать их вклады.

## 2. Архитектурные границы

```text
Browser (React + TypeScript)
  | same-origin HTTPS; HttpOnly cookie; CSRF for mutations
  v
Caddy / reverse proxy
  |-- /*        -> static frontend (SPA fallback)
  `-- /api/*   -> FastAPI (internal network)
                     |
                     +-- auth / students
                     +-- schedule / study
                     +-- applications / notifications
                     |
                     `-- SQLAlchemy -> PostgreSQL

Optional profile "async":
FastAPI -> Celery broker (Redis) -> Celery worker -> PostgreSQL
                                      (idempotent reminders)
```

**Модульный монолит**, один API и одна БД. Точка входа `backend/app/main.py`, бизнес-логика — в доменных модулях, конфигурация и безопасность — в `core/`. Не помещать бизнес-логику в React-компоненты или в роутеры FastAPI.

### Backend-стандарт

- Python 3.12+ как согласованный baseline; FastAPI + Pydantic v2; SQLAlchemy 2.x с явной сессией БД на request; Alembic для каждого изменения схемы. Версии зависимостей закреплены lock-файлом.
- **Фиксированный порядок слоёв:** `router → service → DAO → SQLAlchemy model → PostgreSQL`; `db/dao` обязателен, не заменять его второй системой `repositories`. Структуру и границы ответственности взять из §10 `Task.md`.
- Dependency `get_current_user()` извлекает пользователя только из server-side сессии и проверяет `active`, `expires_at`, `revoked_at`.
- Использовать объект текущего пользователя/студента из dependency, не доверять `user_id` в path/query/body.
- Для чтения приватного объекта условие ownership добавлять **в SQL-запрос**, например `WHERE application.id = :id AND application.student_id = :student_id`. Не получать объект без фильтра, а потом проверять владельца в другом месте.
- Списки всегда ограничены scope текущего пользователя и имеют определённый порядок. Не использовать N+1-запросы на главном экране.
- Переход статуса заявки выполняется атомарно вместе с записью в `application_events`; `created_at`/`updated_at` выставляет сервер.
- Миграции под контролем Alembic: никакого `create_all()` как механизма production schema updates.
- Используй `timestamptz`/UTC и явно конвертируй в `Europe/Moscow` при отображении demo-дней.
- Валидируй вход на границе Pydantic и в бизнес-правилах. Не отдавай внутренние traceback в ответе клиенту.
- §7 `Task.md` — нормативный HTTP/JSON-контракт; OpenAPI генерируется из Pydantic и должен совпадать с примерами. При изменении endpoint'ов исправляй §7, response_model, frontend-типы и contract tests **в одном PR**.
- Логи структурированы и содержат `request_id`, маршрут, статус, длительность; **без** cookie, паролей, полного текста заявки.

### Обязательная структура слоя данных (по образцу `db/dao` на скриншоте)

Агент **не заменяет `dao` слоем `repositories` и не кладёт все SQL-запросы в `services/`**. Структура и имена — из §10 `Task.md`, в частности:

```text
backend/app/
|-- config - pydantic-settings
├── api/v1/                 # FastAPI routers, без SQL
├── schemas/                # Pydantic Request/Response models
├── services/               # ACL, бизнес-правила, транзакции
├── db/
│   ├── __init__.py
│   ├── database.py          # AsyncSession, engine, dependency
│   ├── models/
│   │   ├── __init__.py
│   │   ├── base.py
│   │   ├── user.py
│   │   ├── student.py
│   │   ├── schedule.py
│   │   ├── study.py
│   │   ├── application.py
│   │   └── notification.py
│   └── dao/
│       ├── __init__.py
│       ├── basedao.py
│       ├── user_dao.py
│       ├── login_dao.py
│       ├── student_dao.py
│       ├── schedule_dao.py
│       ├── study_dao.py
│       ├── application_dao.py
│       └── notification_dao.py
└── infrastructure/redis/   # опционально
```

Полное дерево, включая `session_dao.py`, `exam_dao.py`, миграции и тесты, — в §10 `Task.md`; сокращённое дерево выше не отменяет эти файлы. `__pycache__`/`.pyc` в Git не включаются.

**Поток:** `router -> service -> DAO -> SQLAlchemy model -> PostgreSQL`. Router принимает/отдаёт строго типизированный HTTP JSON, **не** делает SQL. Service проверяет текущего студента, запускает сценарий и владеет `commit/rollback`. DAO выполняет только SQLAlchemy запросы, может вызывать `flush`, **не** делает `commit`, не знает `HTTPException`. Models описывают таблицы, ограничения, отношения. `db/database.py` создаёт `async_sessionmaker` и даёт **request-scoped** `AsyncSession`. Для приложений и уведомлений DAO обязан делать ownership filter **в SQL**, например `get_for_student(id, current_student_id)`, а не сначала читать чужой объект.

**Не создавай** публичный универсальный `BaseDAO.get_by_id(id)` для приватных таблиц. `student_id`/`group_id` в DAO поступают только из проверенной server-side записи о студенте. `application_service.create()` атомарно сохраняет `applications` и первый `application_events`; `notification_dao.mark_read_for_student()` обновляет только строку текущего владельца. Изменение схемы = новая Alembic migration + обновление DAO + Pydantic DTO + JSON-контракта + Testcontainers-теста.

### Ruff — обязательные команды агента

Конфигурация Ruff в `backend/pyproject.toml` **строго по §2.1 `Task.md`**. Для каждого backend PR и перед отчётом запустить из `backend/`:

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```

Агент может использовать `uv run ruff check . --fix` и `uv run ruff format .` **до** финальных проверок, но обязан проверить diff. Не заменять Ruff на Black, Flake8 или isort, не скрывать ошибки через массовый `# noqa`. Отдельная проверка типов допустима дополнительно.

### JSON-контракт — не список роутеров

§7 `Task.md` — **обязательная, исчерпывающая спецификация P0 API**. Для каждого endpoint'а перед реализацией сверить: метод + путь, auth/cookie/CSRF/Origin, query/path/body и ограничения, **точную форму успешного JSON с типами и nullable полями**, HTTP status, коды и форму ошибок, owner-scope, тестовую фикстуру. Не отвечать произвольными `{"message":"ok"}` вместо задокументированной формы.

Особенно критично:

- `POST /auth/login` принимает `{"username":"...", "password":"..."}` и отдаёт `{"user": {...}, "session": {"expires_at":"..."}}`; **токен только в HttpOnly cookie**.
- `GET /auth/me` отдаёт `{"user": {...}, "student": {...}}`; `GET /profile` отдаёт профиль без `user_id` из запроса.
- `GET /schedule` принимает `view=today|week`, `date` или `lesson_id` для глубокой ссылки; отдаёт `{"view":..., "timezone":..., "range":..., "items":[...]}`, где перенос имеет `change.before/after`.
- `GET /study` отдаёт `{"summary": {...}, "courses": [...]}`; `GET /exams` — `{"items": [...]}`, только enrollment текущего студента.
- `GET /request-types` отдаёт типы, JSON Schema поля и ограничения. `POST /requests` принимает **`type_code`, `fields`, `comment`**, не `student_id`/`status`, и возвращает **`201` с полным объектом заявки и `history`**. `GET /requests/{uuid}` возвращает такую же форму, чужая заявка — `404`.
- `GET /requests`, `GET /notifications` возвращают `items`/`pagination`, уведомления также `unread_count`; `POST /notifications/{id}/read` — точный `id/read_at/is_read`.
- `GET /dashboard` отдаёт `date/timezone/greeting_name/next_lesson/study/active_requests_count/unread_notifications_count/next_exam/focus`; пустые блоки — `null`/`[]` согласно контракту.
- `POST /auth/logout` возвращает **`204` без JSON**; health не раскрывает данные БД.
- Все ошибки — `{"error": {"code":"...", "message":"...", "request_id":"..."}}`, при `422` добавляется `details`. Чужие и отсутствующие приватные UUID обязаны давать **один и тот же 404**, кроме индивидуального `request_id`.

Frontend-агент не придумывает названия ключей, backend-агент не переименовывает их без правки `Task.md` и согласования. На каждый endpoint пишется contract test `response.status_code` + `response.json()`/Pydantic validation, плюс негативные проверки на неправильный body и чужие данные.


### Auth и безопасность

- Войти: `username + password`. Хешируй пароль **Argon2id**, соль генерируется библиотекой, проверка пароля только сервером.
- Сервер выдаёт криптографически случайный opaque session token; в cookie — оригинал, в Postgres — только его SHA-256 digest. Таблица сессий содержит срок действия и отзыв.
- Cookie в production: `HttpOnly`, `Secure`, `SameSite=Lax`, корректные `Path` и TTL. Не использовать `localStorage`/`sessionStorage` для access/session token.
- Мутации (`POST/PATCH/DELETE`) требуют CSRF-токен и проверки origin; после logout токен невалиден. На login требуй JSON и проверяй `Origin`.
- На login — общий для воркеров rate limit (БД, Redis либо reverse proxy); in-memory лимит для production недостаточен.
- Если пользователь не авторизован → `401`; приватный UUID существует, но принадлежит другому студенту → тот же `404`, что и у несуществующего UUID.
- Демонстрационные пароли задаёт окружение при seed, в хранилище попадают только хеши. `docs` может упоминать demo-логины, но не содержит паролей размещённого демо.
- Минимизируй CORS: если фронтенд и API на одном origin, не разрешай `*` с credentials.
- Приоритет безопасности над удобством: новый feature не может расширять выдачу данных без отдельного security review.

### Frontend-стандарт

- React + TypeScript со строгим `tsconfig`, React Router, TanStack Query. UI-компоненты переиспользуемы, доменные запросы размещаются в `features/` или `app/api`.
- Backend — единственный источник учебных/личных данных. `localStorage` разрешён только для безобидных UI-настроек вроде темы (не для оценок, заявок, персональных данных).
- `fetch`/HTTP client с `credentials: 'include'`; CSRF берётся из `/api/v1/auth/csrf` после login и отправляется заголовком только для мутаций. При `401` сбрасывать приватный cache и возвращать на login.
- После создания заявки и прочтения уведомления инвалидировать соответствующие TanStack Query ключи.
- Любая data page содержит четыре состояния: loading, error с повтором, empty и success. Для submit также pending и success/error.
- На 360 px нельзя скрывать критические действия в hover, делать широченные таблицы или создавать горизонтальный скролл.
- Тексты интерфейса на русском, даты человекочитаемы, ошибки понятны и не раскрывают внутренности системы.
- Доступность: семантические элементы, клавиатура, `focus-visible`, `aria-label`, контраст, `prefers-reduced-motion`; не кодируй состояния только цветом.
- Отображай предупреждение о конкурсном неофициальном характере сервиса на login, footer и странице «О проекте».

### Docker/CI-стандарт

- Для frontend/backend — multi-stage builds, non-root user, `.dockerignore`, проверяемый healthcheck.
- Compose minimum: `db`, `migrate`, `api`, `web`; production наружу публикует только HTTP/HTTPS proxy, не Postgres.
- `migrate` — одноразовая операция; API стартует после успешной миграции и готовности Postgres. Seed вызывается отдельно и является идемпотентным.
- Compose профили позволяют не поднимать worker/beat/Redis в MVP. При Redis/Celery: retry с ограничением, идемпотентные задачи, broker не открыт вовне, периодические job'ы не повторяют уже созданные уведомления.
- CI обязан запускать **Ruff (`ruff check .`, `ruff format --check .`)**, backend typecheck, pytest unit+integration с Testcontainers/Postgres, frontend lint/typecheck/tests/build, E2E (360 px), Docker build, проверку отсутствия секретов. Не пропускать упавшие проверки.
- Production deploy только из успешного CI, с секретами хостинга/runner, после явного разрешения владельца. Никаких ключей в коммитах, скриншотах или stdout.
- Документировать способ проверки доступа из РФ; не считать его выполненным только по `curl` с локального сервера.

## 3. Агенты и разделение ответственности

В небольшом проекте эти роли может последовательно выполнять один ИИ-ассистент. Для параллельной работы назначайте отдельные ветки/области файлов, не давайте агентам одновременно править `compose.yaml`, миграции или общие API DTO.

| Роль | Владелец результата | Ключевые deliverables | Что обязательно проверить |
|---|---|---|---|
| **Orchestrator / Tech Lead** | Технические решения и порядок задач | План срезов, ADR, последовательность, синхронизация контрактов | Все P0, отсутствие дублирования и работы «вперёд» без базы |
| **Backend Agent** | FastAPI, Postgres, auth, доменные модули | JSON DTO, `db/models`, `db/dao`, `services`, Alembic, seed и pytest | Ownership в SQL, **Ruff**, точный JSON §7, hash, CSRF, commit в service |
| **Frontend/UX Agent** | Мобильный React-интерфейс | Login, app shell, dashboard, расписание, study, requests, notifications | 360 px, клавиатура, loading/error/empty, реальные запросы API |
| **QA/Security Agent** | Негативные сценарии и стабильность | Test matrix, pytest/Testcontainers, Playwright, security audit | IDOR A→B, авторизация, утечки, подмена id, logout, сохранность |
| **DevOps Agent** | Compose, Caddy, CI/CD, staging/prod | Dockerfiles, healthchecks, migrations, workflow, deploy guide | Нет наружного Postgres, HTTPS, secrets, доступность из России |
| **Evidence/Documentation Agent** | Доказательства разработки с ИИ | README, ai-process, скриншоты, demo-script, security explanation | Никаких выдуманных диалогов/скринов/проверок |

**Передача работы между ролями:** каждая завершённая задача заканчивается коротким отчётом: цель, изменённые файлы, миграции, endpoints, тесты и их реальный статус, риски, ручная проверка и следующий шаг. Если тесты не запускались, прямо писать `НЕ ЗАПУЩЕНЫ` с причиной.

## 4. Рабочий цикл: одна законченная вертикаль за раз

**Шаг A — план.** Orchestrator выбирает конкретный checkbox в `Task.md`, описывает пользовательский сценарий, ограничивает файлы и формирует `Definition of Done`.

**Шаг B — контракт.** Backend Agent **берёт request/response JSON, HTTP status, ошибки, заголовки, query/path и nullable поля из §7 `Task.md`** и согласует scope, DAO-методы, таблицы/индексы, миграции и тесты. Frontend Agent получает стабильные DTO/примеры из OpenAPI, а не придумывает формат ответа самостоятельно.

**Шаг C — реализация.** Backend реализует model/migration/DAO/service/router/Pydantic DTO/pytest; frontend — реальные запросы и полные UI-состояния; DevOps обеспечивает запуск. Не завершать задачу на этапе «отдаёт JSON из списка в памяти».

**Шаг D — негативные проверки.** QA запускает реальную БД в Testcontainers и сценарии пользователя B; при обнаружении IDOR/CSRF сначала закрыть уязвимость, затем продолжать UI-polish.

**Шаг E — интерфейс и интеграция.** Проверка на 360 px и desktop, пустые данные, offline/error API, expired session и повторная отправка.

**Шаг F — документирование.** Обновить README/архитектуру/API и `docs/ai-process.md`, приложить реальные скриншоты, зафиксировать ошибки ИИ и способы их исправления.

**Шаг G — review.** Независимый Reviewer ищет утечки, невалидные допущения, неиспользуемые сервисы, сломанные миграции, незаполненные состояния и случайно зашитые секреты. После review принимается следующий чекбокс.

## 5. Границы самостоятельности агентов

**Можно выполнять автономно:** создавать и редактировать код и тесты в репозитории; добавлять миграции; локально запускать Compose/testcontainers; писать документацию; фиксировать искусственно сгенерированные demo-данные; предлагать компромиссы архитектуры.

**Нужно согласовать с человеком:** выбор публичного домена и платного хостинга, любой деплой в production, публикацию учётных данных для жюри, изменение продукта вне `Task.md`, включение платной LLM, работу с секретами, любые необратимые операции с БД.

**Запрещено:** обращаться к системам настоящего вуза, собирать реальные персональные данные, переносить содержимое приватных файлов в сторонние LLM, обходить тесты ради зелёного CI, утверждать, что внешняя доступность проверена без соответствующей проверки.

## 6. Контрольный набор тестов (обязателен для MVP)

### Backend / pytest + Testcontainers

1. Контрактные тесты в каждом модуле роутера проверяют API-ответы, статусы, nullable поля и `422/404` по §7 `Task.md`.
2. `test_login_and_me_for_two_students` — логины A и B возвращают разные профили.
3. `test_login_wrong_password_and_rate_limit` — неверный пароль отклоняется, лимит работает между процессами/воркерами (интеграционное подтверждение механизма).
4. Тесты приватных роутеров проверяют `401 UNAUTHORIZED` при отсутствии сессии.
5. `test_logout_revokes_session` — повторное использование токена после logout невозможно.
6. `test_mutation_rejects_missing_or_bad_csrf` — отсутствие/подмена CSRF → 403.
7. `test_student_cannot_read_other_application` — для UUID заявки B пользователь A получает 404.
8. `test_student_cannot_set_request_owner_in_payload` — подмена владельца в JSON игнорируется либо даёт 422, запись остаётся за A.
9. `test_student_cannot_mark_foreign_notification_read` — чужое уведомление не меняется.
10. `test_schedule_scoped_to_group` — подмена group ID не даёт пар чужой группы.
11. `test_grades_scoped_to_enrollment` — чужие дисциплины/оценки не попадают в ответ.
12. `test_application_persists_and_has_history` — создание 201, read after reconnect, event `new`.
13. `test_week_boundaries_and_lesson_changes` — Sunday/Monday и переносы с корректной зоной.
14. `test_seed_is_idempotent` — повторное наполнение не дублирует пользователей/заявки.
15. `test_migrations_apply_to_fresh_database` — на чистом Postgres миграции проходят из нуля.

**Обязательное условие:** интеграционные тесты поднимают настоящий PostgreSQL через `testcontainers[postgres]`, а не SQLite. Миграции применяются так же, как в production. Тесты независимы, фиксируют данные/время, не используют живой demo-сервер.

### Frontend / Playwright

- Логин A → главная → сегодня → неделя → оценки → новая заявка → статус → refresh → уведомление → logout.
- Логин B → свои данные, отсутствие заявки A, собственное расписание.
- На **360×800** и **390×844** нет горизонтального переполнения, модальные окна/формы доступны и отправляются.
- При искусственной ошибке API виден recovery/action, не пустой белый экран.
- При `401` после истечения сессии пользователь переходит на login и прежний cache не показывается.
- При изменении расписания понятно, какие данные были исходными, а какие новыми.

### CI quality gate

```text
backend:  uv run ruff check . + uv run ruff format --check . + typecheck + pytest-unit + pytest-integration + coverage строк ≥80%
frontend: lint + typecheck + unit + coverage строк ≥80% + build + Playwright smoke
infra:    compose config + Docker builds + secret scan
release:  manual smoke на production + два тестовых логина + 360 px + РФ-доступность
```

Не превращать этот блок в фальшивые команды. Конкретные команды появляются в README/CI **после** выбора package manager и инициализации проекта.

## 11. План разбора типичных ошибок ИИ

| Если агент… | Реакция |
|---|---|
| Отдал чужие оценки по `?student_id=` | Отвергнуть PR, перенести авторизацию в server dependency + SQL-фильтр, написать отрицательный тест A/B |
| Сделал «заявка отправлена» без сохранения | Реальная миграция/POST/COMMIT, Testcontainers-тест после повторного чтения |
| Использовал SQLite для интеграции | Оставить SQLite только для локальных unit-тестов без DB-специфики; интеграцию переделать на PostgreSQL/Testcontainers |
| Спрятал кнопку вместо ACL | Проверить прямой HTTP-запрос по чужому UUID, исправить endpoint |
| Положил пароль в `.env.example` или seed | Удалить значение, заменить placeholder, проверить историю Git и при необходимости ротировать опубликованный секрет |
| Предложил Redis/Celery до работающего MVP | Отложить в P1, закончить сценарии из S1–S6 |
| Сломал адаптив на 360 px | Добавить Playwright проверку переполнения и исправить конкретный компонент |
| Сочинил «историю промптов» для отчёта | Удалить вымысел, включить реальные чаты/скриншоты и обозначить отсутствующие доказательства |
| Сказал «зелёные тесты», но не запускал | Пометить `NOT RUN`, запустить или описать воспроизводимую блокировку |
| Сделал хрупкую CI-конфигурацию | Воспроизвести команды локально/в CI, починить причины, не выставлять `continue-on-error` для обязательных тестов |
| Смешал SQL с router/service | Перенести выборки в `db/dao`, транзакцию в service, проверить Testcontainers |
| Ответил произвольным JSON (`data`, `message`) | Сверить §7 `Task.md`, Pydantic `response_model`, обновить contract test и frontend типы |
| Пропустил Ruff или отключил его правила | Восстановить команды и `pyproject.toml`, исправить реальные ошибки, показать CI |
